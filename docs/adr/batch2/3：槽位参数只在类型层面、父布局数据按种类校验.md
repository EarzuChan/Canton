# 003 槽位参数只在类型层面、父布局数据按种类校验

日期 2026-11-22。

## 背景

[batch1 ADR 002](../batch1/2：Slot句柄与父布局数据.md) 定了槽位传参的写法，以及“父布局数据经 Handle 构造、原生按实际父级校验”。M2 落地时有几处它没有说到：参数在运行期要不要有声明、`&` 的值能写什么、原生校验细到什么程度、Compose 的 Scope 上有而 Canton 还没有的能力补不补。本文补定这几处，不改 ADR 002 的约定。

## 决定

槽位参数：

- **参数只存在于类型**。定义在运行期只登记槽位名；出口把实参组成一个对象，按值传给内容函数。HMR 的契约判定因此只计槽位名。
- **`&` 绑定就是内容函数的形参解构**。值可以是别名，也可以是解构模式；别名、默认值、嵌套、rest 和遮蔽都是 JS 自身的语义，编译器不另行实现。
- **实参是出口的结构输入**：在出口自己的内容作用域里求值，变化只重跑这个出口的内容。
- **类型由编译产物里的 `satisfies` 给出**：每次调用的内容表按“定义 + 本次调用的参数”约束，转译时擦除。类型检查和值单位分析共用这份产物，`&` 的局部名在两边是同一个类型。参数类型随调用参数变化的定义（Lazy 的 `item`、Crossfade 的 `state`、DynamicArrangable 的各槽位）另挂一个只存在于类型的 `slotTypes`。
- **要逐项、逐层给内容的内建件收内容，不收定义**：Lazy 四件套和 Crossfade 不再接收 Arrangable 定义和参数映射，改由默认槽交付 `item`、`index`、`state`。
- **Handle 的片段可以直接起头往下链**，`then()` 只在要插到链中间时才需要。

父布局数据：

- **原生按数据种类校验，不记来源**。`matchParentSize` 只认 Box；`weight` 认 Row、Column、Flow；`align` 按实际父级的交叉轴方向核对；`alignBy` 认 Row 和 FlowRow；交叉轴填充认 Flow；按视口填充只能用在 Lazy 项内。父级不认的一律报错，不静默忽略。
- **能力补齐的线**：Compose 的 Scope 上有而 Canton 没有的能力，只涉及测量、能用 C++ core 用例验住的，随 Handle 一起补；要靠上屏画面验收的（`animateItem`）和要在测量中途回调脚本的（回调形式的 `alignBy`）移交后续里程碑。

## 为什么不选别的

- **运行期也登记参数**，用来诊断“绑定了出口没传的参数”：这类错误类型检查已经能报。运行期再记一份，HMR 就得把参数变化算进契约，改一个参数类型也要重挂载。
- **参数做成响应式对象，按读取位置追踪**：ADR 002 定的是“实参变化按该出口的结构输入更新”。按值传入时解构就是普通 JS；做成响应式对象，解构会丢掉追踪，又得另写一套绑定语义。
- **只在类型检查的产物里约束内容表**：值单位分析看不到槽位参数的类型，`rowHandle.weight(1).size(20.dp, 10.dp)`、`M.height(item.height.dp)` 里的单位无法正确降级。
- **Lazy、Crossfade 继续收定义**：每项内容都得拆成单独的 `.cta` 再配一个参数映射函数，项内也拿不到 Handle。
- **父布局数据带上来源布局种类或容器实例身份**：能多拦两种情形，一是 `weight` 在 Row、Column、Flow 之间互传，二是外层容器的 Handle 用在内层同种容器的子项上。两者数据种类相同，布局结果也符合预期；为此每份数据都要多带来源，收益小。Compose 在这里更松：Scope 是无状态单例，父布局读到种类不符的数据就静默忽略，只靠编译期的 `@LayoutScopeMarker` 拦。

## 代价

- 运行期不诊断“绑定了出口没传的参数”，没过类型检查的代码按 JS 解构规则拿到 `undefined`。
- TS 手写的定义若参数类型随调用参数变化，要手工写 `slotTypes` 并做一次类型断言。
- 上述两种互传情形不报错。
