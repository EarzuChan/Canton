# 文档维护规范

本目录仅用于记录**代码本身无法直接表达的信息**。文档必须保持精简，严禁把代码实现用自然语言再复述一遍。

## 核心原则

1. **代码即实现事实源**：具体怎么实现、接口长什么样，一律以源码和注释为准，不在文档中抄写或复述实现细节。
2. **一件事只在一个地方讲透**：需要引用其他文档的概念时，只提名字并给相对路径链接，不重复展开。
3. **说人话，禁黑话**：以中文为主（保留必要英文术语），客观直白。严禁堆砌空洞词汇（如“链路闭环、语义冻结、重塑新一代基础设施”）。

## 目录结构

docs/
├ README.md # 本文件：文档规则
├ ARCHITECTURE.md # 系统地图（只需 1 篇）
├ adr/ # 架构决策记录（按时间编号，如 001-xxx.md）
└ proj/ # 项目推进与待办
   ├ roadmap.md # 项目目标、远期想法与里程碑总表
   └ m<N>.md # 当前里程碑的任务清单与进度（简单里程碑用单文件即可）

### `ARCHITECTURE.md`（系统地图）
- **写什么**：核心模块划分、目录导航、关键数据流（优先用 Mermaid 图）、系统级的硬约束与边界。
- **不写什么**：具体的类/函数实现、开发进度、历史妥协过程。
- **要求**：随系统演进直接更新，始终反映**当前真实架构**。如果发现这篇文档越来越长，说明你把不该写的实现细节塞进来了，必须删减。

### `adr/`（为什么这么做）
- **写什么**：遇到分歧、踩坑或做重大技术取舍时，记录“背景 -> 选了什么 -> 为什么不选别的 -> 代价是什么”。
- **不写什么**：不写大段 API 规范，不写流水账。常规、显而易见的改动不需要写 ADR。
- **规则**：
    - 一事一议，力求短小（通常半页以内）。
    - **只增不改**：历史 ADR 严禁修改正文。若某决策已被推翻，仅在旧篇目顶部加一行 `> 状态：已废弃，被 [ADR-xxx](./xxx.md) 替代`。

### 3. `proj/`（现在做什么）
- `roadmap.md`：项目最终要做成什么样、各里程碑目标、暂不做的远期想法。
- `m<N>.md`（或复杂时建 `m<N>/` 目录）：当前阶段的拆解任务、Checklist 与临时笔记。
- 里程碑结束后，只把少数真正需要长期保留的决策提取成 ADR，或更新到 `ARCHITECTURE.md`，其余过程文件留在原处归档即可，无需额外写审计报告。

## 事实冲突时的判定顺序

1. **当前代码**（具体行为与接口的最高事实源）
2. **`ARCHITECTURE.md`**（模块边界与全局约定的最高事实源）
3. **最新的有效 `adr/`**（设计意图的依据）
4. **`proj/` 下的文件**（仅代表临时计划，无权覆盖上述三项）

若发现代码与 `ARCHITECTURE.md` 不一致，视为 Bug 或文档过期，应请示主人后顺手修平其中之一。
